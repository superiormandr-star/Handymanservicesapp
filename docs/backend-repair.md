# ProConnect backend repair and release gate

## Confirmed root cause
Production deployment dpl_ASr7wranqxZT4HQYVAXgFKYHwEbT serves main commit 16cfd41. Its build logs complete in 86ms without creating an API function. main has neither api/index.js nor vercel.json and server.js unconditionally starts a persistent HTTP listener. Static public pages therefore load while API paths return 404. Additionally, /api/documents was not an application route: the UI uses /api/command/estimates and /api/admin/documents. The repair provides an owner-protected compatibility alias.

Historical commit 8ac41fb contained a D1 adapter and Microsoft workflow; those files are absent from current main. Production still has SPC_STORAGE_URL, signing/encryption keys and an admin token. The owner's screenshots report the old Cloudflare endpoint returning 404 and a newly created, incompletely connected private Vercel Blob store. A configured token does not prove that customer data exists there. The owner has since confirmed that ProConnect has no existing records or subscribers. This authorizes initialization of an empty production store, with no seeded business records. Superior Maintenance remains separate.

## Storage configuration
Select SPC_STORAGE_BACKEND=blob explicitly for private Vercel Blob. Keep the existing BACKUP_ENCRYPTION_KEY private and unchanged. Configure BLOB_READ_WRITE_TOKEN in Vercel secrets. Default production object: superior-proconnect/production/state.json.enc. SPC_BLOB_PATH can select an existing compatible envelope within that namespace. The adapter preserves the entire JSON envelope, including unknown collections and OAuth state. Reads bypass the CDN cache. Writes use the canonical control-plane ETag checked before and after an uncached content read, and return 409 on conflict; immutable encrypted history is written before the conditional update. A failed history upload prevents the update. This is a small single-snapshot store with optimistic concurrency, not a relational database; sustained write traffic should move to transactional Postgres through the same request adapter.

The historical D1 adapter remains available with SPC_STORAGE_BACKEND=d1 for recovery after its endpoint is independently verified. Never silently switch between stores. Missing, corrupt, inaccessible or undecryptable data returns 503; Vercel never falls back to JSON files and never seeds records. Runtime initialization is forbidden on Vercel even if SPC_ALLOW_INITIALIZE is set.

Preview deployments require a preview- namespace and must use synthetic records and separate credentials. Both SPC_PERSISTENCE_VERIFIED and SPC_WRITES_ENABLED default to false. These flags gate all mutations including Microsoft connection/callback and backup operations. Setting them is an operator attestation, not an automated proof of persistence.

## Record recovery and release sequence
1. Locate and privately export every existing record source (old D1, prior Node host DATA_FILE, owner exports, backups, and the Blob inventory). Account for estimates, invoices, customers, reviews, subscriptions, profiles and CRM collections. Do not infer an empty business database from an empty folder or a 404. Preserve encrypted originals and keys. Only ProConnect data belongs here; do not access the independent Superior Maintenance system.
2. Compare counts and identifiers, resolve duplicates without deleting records, and review the complete recovered snapshot. No production import is authorized by a successful synthetic test alone.
3. For a new destination only, run scripts/import-blob.cjs with a reviewed complete private JSON export and namespace. It validates collections, encrypts the full envelope and refuses overwrite. It never runs during build/startup. Plain records imports have empty Microsoft OAuth state and require reconnection; full {records,oauth} exports preserve it. Existing encrypted objects require recovery with the original key before import. No automatic format conversion or destructive restore exists.
4. In a separate preview namespace, import a complete synthetic dataset, enable the two write flags only there, then test authentication, create/save/retrieve estimate, customer approval, exactly one generated invoice, payment recording, print/PDF and export. Change the deployment and repeat retrieval from a fresh function instance. Compare identifiers and hashes from both deployments. Test concurrent edits return 409. Review network/console and mobile layouts for all three existing site experiences. The real private Blob cross-deployment exercise has now passed, including an estimate, approval-generated invoice and payment status retained across new deployments.
5. Confirm the production object contains the reconciled records through an authenticated read-only staged production deployment. Review the staged commit and tests. Only then enable production writes, test using explicitly synthetic records, connect Microsoft, verify backups, and promote the tested deployment. Never seed production to make health green. Keep current production serving until these prerequisites are met.

## OneDrive
Recovered onedrive.js uses OAuth state, PKCE, durable encrypted refresh tokens and AppFolder scope. Register APP_ORIGIN + /api/auth/microsoft/callback in Microsoft Entra and configure the tenant, client and client secret in Vercel secrets. /backups.html requires the owner token (held in memory). It reports the last verified backup. Uploads encrypt the full record snapshot, download it and compare checksums; recovery downloads only, never replaces live data. vercel.json schedules /api/cron/backup daily at 07:17 UTC with CRON_SECRET bearer authentication. Enable only after primary persistence is verified and the account is connected. Monitor scheduled execution and perform a synthetic recovery comparison before claiming automatic backups work.

The existing GitHub OneDrive verification workflow uploads only synthetic verification payloads. It is not a customer-record backup and is not evidence of scheduled record protection.
